## 1. Overview

NetRank's match system manages the complete lifecycle of a competitive match - from an initial
challenge proposal through acceptance, score submission, dispute resolution, and final Elo rating
updates. The system is implemented across two Flask blueprints (`/api/matches` and
`/api/match-rules`) with a layered permission model based on account roles: **Administrator**,
**ClubOwner**, and **TeamManager**.

Core design principles:

- All state is stored in dedicated 1-to-1 extension tables (`match_accepted`, `match_rejected`,
  etc.) hanging off a single `match_proposal` root record.
- Match rules use an immutable-by-design pattern: editing a rule creates a new successor record
  and deactivates the old one, preserving a full audit trail.
- Score submission is a two-sided consensus flow - both team sides submit independently, and the
  match is auto-finalized only when they agree. Disputes are escalated to a ladder admin.
- Weekly match proposals are auto-generated by rank-based pairing within a ladder, gated by
  player availability overlap and a rematch cooldown policy.

## 2. Data Model

### 2.1 Core Tables

| Table | Description |
|---|---|
| `match_proposal` | Root record for every match. Always exists. Holds teams, sport type, ruleset, ladder reference, status, and optional location/timing. |
| `match_status` | Lookup table seeded with: pending (1), accepted (2), rejected (3), played (4), cancelled (5). |
| `match_accepted` | 1-to-1 extension. Created when team2 accepts. Stores responding user and optional message. |
| `match_rejected` | 1-to-1 extension. Created when team2 rejects. |
| `match_played` | 1-to-1 extension. The authoritative final score. Written once by `finalize_match()`, never directly by an API caller. |
| `match_cancelled` | 1-to-1 extension. Created when team1 cancels an accepted match. |
| `match_score_submission` | Up to 3 rows per match (one per role: `team1_side`, `team2_side`, `ladder_admin`). Enforced by a UNIQUE (match_id, role) DB constraint. |
| `match_rule` | A single rule (e.g. "no coaching"). Supports immutable versioning via `is_active` / `replaced_by`. |
| `match_rule_set` | A named, ordered collection of `MatchRule` references. May be attached to a Ladder. |
| `match_rule_set_rule` | Junction table: many-to-many between rule sets and rules. |

### 2.2 MatchProposal Key Fields

| Field | Description |
|---|---|
| `team1_id` / `team2_id` | Teams involved. `team1` is always the proposing side. CHECK constraint enforces they differ. |
| `status_id` | FK to `match_status`. Drives the lifecycle state machine. |
| `ladder_id` | Optional. When set, the match counts towards a ladder ranking and the ladder's ruleset is used. |
| `ruleset_id` | Legacy direct FK to a rule set. Superseded by `ladder_id` when present. |
| `rule_snapshot` | JSONB. Frozen copy of the effective ruleset at proposal creation time. |
| `week_start_date` | ISO date of the Monday of the target week. Auto-generated proposals carry this; friendly matches may omit it. |
| `proposed_start_at` | Computed from player availability overlap. May be NULL for manual proposals. |
| `score_status` | Computed property (not a DB column): `not_submitted`, `disputed`, `resolved`, or `cancelled`. |

### 2.3 Submission Roles

Each match can receive at most three score submissions, one per role:

- `team1_side` - a manager or ClubOwner authorised to act on behalf of team1.
- `team2_side` - same, but for team2.
- `ladder_admin` - a ClubOwner of the ladder's club, or an Administrator. May only submit when
  team sides have already submitted and disagree.

## 3. Match Lifecycle

### 3.1 Stage 1 - Proposal Creation

**Endpoint:** `POST /api/matches`

Any TeamManager of either team, a ClubOwner of their club, or an Administrator may create a
proposal. Required and optional body fields:

| Field | Required | Type | Notes |
|---|---|---|---|
| `team1Id` | yes | int | Proposing team |
| `team2Id` | yes | int | Challenged team (must differ) |
| `sportTypeId` | yes | int | |
| `rulesetId` | no | int | |
| `ruleSnapshot` | no | JSON | Frozen snapshot of ruleset rules |
| `location` | no | string | |
| `venueTypeId` | no | int | |

The match is created with `status = pending`.

### 3.2 Stage 2 - Accept or Reject

**Endpoints:** `POST /api/matches/<id>/accept` | `POST /api/matches/<id>/reject`

Only managers of **team2** (the challenged side) or an Administrator may accept or reject.
The match must be in `pending` status. An optional `responseText` message can be included.

- On accept: a `match_accepted` row is created and status moves to `accepted`.
- On reject: a `match_rejected` row is created and status moves to `rejected`. This is a terminal state.

### 3.3 Stage 3 - Score Submission (Two-Sided Consensus)

**Endpoint:** `POST /api/matches/<id>/score`

This is the primary result-recording flow. Each manager submits their version of the score:

1. `team1_side` submits - score is stored; `score_status` remains `not_submitted`.
2. `team2_side` submits:
   - If scores **agree** - `finalize_match()` is called automatically. `MatchPlayed` is written,
     Elo ratings updated, `status = played`.
   - If scores **disagree** - match enters `score_status = disputed`. No `MatchPlayed` is written.
3. (only if disputed) `ladder_admin` submits the decisive score - `finalize_match()` is called
   with the admin's numbers.

The service layer (`match_score_service.submit_score`) handles role resolution, guards, and
auto-finalization atomically. The caller never writes `MatchPlayed` directly.

### 3.4 Stage 3 (Legacy) - Direct Result Submission

**Endpoints:** `POST /api/matches/<id>/result/check` | `POST /api/matches/<id>/result`

An older flow that allows a single authorised manager to submit a result directly, bypassing
two-sided consensus.

- `/result/check` - dry-run: validates the payload and warns if a result already exists without
  writing anything.
- `/result` - unconditionally writes `MatchPlayed` and triggers Elo updates. Re-submitting the
  identical score returns 200 (idempotent retry); a different score on an already-played match
  returns 409.

### 3.5 Stage 4 - Cancellation

**Endpoint:** `POST /api/matches/<id>/cancel`

Only managers of **team1** (the proposing side) or an Administrator may cancel. Cancellation is
only possible when `status = accepted`. A `match_cancelled` row is created with an optional
`reason`, and status moves to `cancelled`.

## 4. Listing Endpoints

All listing endpoints support `?from=<offset>&to=<exclusive_upper>` pagination (default: 0-20).

| Endpoint | Auth | Who can call | Description |
|---|---|---|---|
| `GET /api/matches/active` | Public | Anyone | All matches with `status=accepted` (not yet played). |
| `GET /api/matches/played` | Public | Anyone | All matches with `status=played` (have a final score). |
| `GET /api/matches/pending` | Required | TeamManagers of challenged team | Pending proposals where the caller manages team2. Admins see all. |
| `GET /api/matches/awaiting-result` | Required | TeamManagers of either team; Admin | Accepted matches where the caller can submit a score. |
| `GET /api/matches/disputed` | Required | ClubOwner of ladder's club; Admin | Matches in `disputed` score_status that the caller can adjudicate. |
| `GET /api/matches/<id>/score` | Required | Managers of either team; Admin | Returns all score submissions and current `score_status` for a match. |

## 5. Permission Model

### 5.1 Role Hierarchy

The system uses a `resolved_role` pattern: `account.resolved_role` returns the most-specific ORM
object (`Administrator > ClubOwner > TeamManager`). All permission checks branch on this type.

| Role | Access |
|---|---|
| `Administrator` | Unrestricted access to all match operations. |
| `ClubOwner` | Can manage matches for any team belonging to their club(s). Can also adjudicate disputed scores for matches on ladders owned by their club. |
| `TeamManager` | Can manage matches only for teams where `TeamManagerTeam.can_manage_match = True`. Cannot adjudicate disputes. |

### 5.2 Operation-Level Rules

| Operation | Required permission |
|---|---|
| Create proposal | Must manage at least one of team1 or team2 (`_can_manage_either_team`). |
| Accept / Reject | Must manage **team2** specifically (`_can_manage_match` on team2). |
| Submit result (legacy) | Must manage team1 or team2. |
| Submit score (new flow) | Must manage team1 (-> `team1_side`) or team2 (-> `team2_side`), or be a ladder admin (-> `ladder_admin`). |
| Cancel | Must manage **team1** specifically. |
| Adjudicate dispute | Must be an Administrator, or a ClubOwner of the ladder's club (`can_adjudicate_score`). |

## 6. Match Rules and Rule Sets

### 6.1 MatchRule

A `MatchRule` is a named text entry describing one rule of play (e.g. "Best of 3 sets",
"No coaching allowed"). Features:

- **Public/private visibility** via `can_be_used_by_others` flag.
- **Club scope** via `club_id` to restrict a rule to a specific club.
- **Immutable versioning**: editing the name or description does NOT modify the row. Instead, a
  new `MatchRule` row is created (the successor) and the old one is marked `is_active = False`
  with `replaced_by = successor.id`. This preserves the historical state of any match that
  referenced the old rule via `rule_snapshot`.

### 6.2 MatchRuleSet

A `MatchRuleSet` is a named collection of `MatchRule` references. Rule sets can be linked to
`Ladder` objects and optionally snapshotted on match proposals. Operations:

- Create or delete the set.
- Rename or update description.
- Add a rule: the caller must own the rule set and be permitted to use the rule (public rule, or
  own private rule).
- Remove a rule from the set.

### 6.3 Rule Endpoint Reference

| Endpoint | Auth | Who can call | Description |
|---|---|---|---|
| `GET /api/match-rules` | Public | Anyone | List all active, public rules (paginated). |
| `GET /api/match-rules/<id>` | Public | Anyone | Get a single rule by ID. |
| `POST /api/match-rules` | Required | Any authed user | Create a new rule. |
| `DELETE /api/match-rules/<id>` | Required | Owner / Admin | Delete a rule. |
| `PATCH /api/match-rules/<id>/name` | Required | Owner / Admin | Immutable rename: creates successor, deactivates old. |
| `PATCH /api/match-rules/<id>/description` | Required | Owner / Admin | Immutable description update. |
| `PATCH /api/match-rules/<id>/deactivate` | Required | Owner / Admin | Mark rule inactive (no successor). |
| `PATCH /api/match-rules/<id>/replace` | Required | Owner / Admin | Deactivate and point to an existing successor rule. |
| `GET /api/match-rule-sets` | Public | Anyone | List all public rule sets (paginated). |
| `GET /api/match-rule-sets/<id>` | Public | Anyone | Get a single rule set. |
| `POST /api/match-rule-sets` | Required | Any authed user | Create a new rule set. |

## 9. HTTP Error Reference

| Code | Meaning in this system |
|---|---|
| 400 | Missing or non-JSON request body. |
| 401 | Authentication required (no valid session cookie / token). |
| 403 | Authenticated but insufficient permissions for this operation. |
| 404 | Entity not found (match, team, rule, rule set). |
| 409 | Conflict: invalid state transition, duplicate submission, or already-played result. |
| 410 | Gone: rule is inactive (replaced by a newer version). |
| 422 | Validation error: missing required field, invalid type, or business rule violated (e.g. same-team match, negative score, same name as current). |
